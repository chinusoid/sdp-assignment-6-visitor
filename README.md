# Assignment 6 — Visitor

Простой консольный проект на Java по теме «Прокат оборудования астрономического клуба». Visitor позволяет добавлять операции над телескопами и звёздными проекторами без изменения классов оборудования. Внешних библиотек и комментариев в коде нет.

## Запуск

Нужен JDK 8 или новее. Выполнить из папки проекта:

```sh
mkdir out
javac -d out src/*.java
java -cp out Main
```

Если папка `out` уже существует, первую команду можно пропустить.

## Результат

```text
Packing list:
Moon telescope: tripod, eyepiece, lens cap
Indoor star projector: power cable, remote control
Planet telescope: tripod, eyepiece, lens cap
Rental for 2 days: 26000 KZT
Telescopes: 2
Star projectors: 1
```

Для примера заданы условные тарифы: телескоп — 5000 KZT в день, проектор — 3000 KZT в день. Для двух телескопов и одного проектора на два дня стоимость равна `(5000 + 3000 + 5000) * 2 = 26000 KZT`. Данные и число дней задаются в `Main`.

## Компоненты Visitor

| Роль | Класс или интерфейс | Назначение |
| --- | --- | --- |
| Element | `Equipment` | Объявляет `accept(EquipmentVisitor visitor)` |
| Concrete Elements | `Telescope`, `StarProjector` | Хранят название и вызывают соответствующий метод посетителя, передавая `this` |
| Visitor | `EquipmentVisitor` | Объявляет `visitTelescope` и `visitStarProjector` |
| Concrete Visitor | `RentalCostVisitor` | Считает общую стоимость аренды |
| Concrete Visitor | `PackingListVisitor` | Выводит список принадлежностей для упаковки |
| Третий посетитель | `InventoryVisitor` | Считает количество объектов каждого типа |
| Object Structure | `List<Equipment>` в `Main` | Содержит разные типы оборудования |
| Client | `Main` | Обходит коллекцию и вызывает `accept` для каждого посетителя |

## Двойная диспетчеризация

Рассмотрим `item.accept(packingList)`, когда `item` содержит телескоп.

1. Тип переменной `item` — `Equipment`, но Java выбирает `Telescope.accept` по фактическому типу объекта.
2. Внутри `Telescope.accept` выполняется `visitor.visitTelescope(this)`. Java выбирает реализацию `PackingListVisitor.visitTelescope` по фактическому типу посетителя.

Таким образом, выполняемый код зависит и от типа оборудования, и от типа посетителя. Для проектора вызывается `visitStarProjector`. Проверять тип через `instanceof`, приведение типов или цепочку условий не нужно.

## Принципы Clean Code

1. **Понятные имена.** `Equipment` обозначает элементы, а суффикс `Visitor` выделяет операции. `getTotal`, `telescopeCount` и `days` показывают назначение данных.
2. **Единственная ответственность.** `RentalCostVisitor` считает стоимость, `PackingListVisitor` составляет список для упаковки, `InventoryVisitor` считает оборудование. Классы элементов хранят данные и принимают посетителя.
3. **Полиморфизм вместо проверки типов.** Каждый элемент вызывает свой `visitX(this)`. В исходниках нет `instanceof`, `getClass` или условий для определения типа оборудования.
4. **Инкапсуляция.** Названия хранятся в `private final` полях. Для упаковки посетителю нужен доступ к названию, поэтому предоставлен только `getName()`. Он раскрывает необходимые данные, но не позволяет их изменить. Счётчики посетителей также закрыты и доступны через методы чтения.
5. **Открытость для расширения.** `InventoryVisitor` добавляет третью операцию, реализуя существующий `EquipmentVisitor`. Для его подключения достаточно создать объект в `Main` и передать его в `accept`; менять элементы, интерфейсы и другие посетители не требуется.
6. **Небольшие методы.** Каждый `visitX` выполняет одну короткую операцию. `accept` содержит только передачу управления посетителю.
7. **Именованные константы.** Тарифы названы `TELESCOPE_DAILY_RATE` и `PROJECTOR_DAILY_RATE`, поэтому их смысл понятен и значения легко заменить.

## Кратко для защиты

**Почему здесь подходит Visitor?** Типы оборудования стабильны, а операции различаются: расчёт денег, подготовка к упаковке и инвентаризация. Новую операцию можно добавить отдельным посетителем.

**Как добавить ещё одного посетителя?** Создать класс, реализующий оба метода `EquipmentVisitor`, затем создать его в `Main` и вызвать `accept` для каждого элемента коллекции. Существующий `InventoryVisitor` показывает такое расширение.

**Что произойдёт при добавлении нового типа оборудования?** Нужно создать новый элемент, добавить соответствующий метод в `EquipmentVisitor` и реализовать его во всех посетителях. Это основной недостаток Visitor: новые операции добавляются легко, новые типы элементов требуют больше изменений.

**Где находятся результаты?** Стоимость и количество объектов накапливаются в полях соответствующих посетителей. `PackingListVisitor` сразу выводит строки. Каждый накопительный посетитель создаётся заново для одного обхода: повторный обход тем же объектом снова прибавит результаты.

**Почему нет отдельного класса коллекции?** `List<Equipment>` уже выполняет роль Object Structure. Дополнительная оболочка не нужна для этого небольшого примера.
